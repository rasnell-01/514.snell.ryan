## Question 1: Practice with OCaml Pattern Matching

```ocaml
type 'a rose = Node of 'a * 'a rose list
```

A rose tree is a node holding a value plus a *list* of child trees
(as opposed to a fixed-arity tree like a binary tree).

### `size`

```ocaml
let rec size (Node (_, children)) : int =
  1 + List.fold_left (fun acc child -> acc + size child) 0 children
```

A node always contributes 1 for itself. `List.fold_left` walks the
list of children, calling `size` on each one recursively and adding
the results together, so the total is "1 (this node) + the sizes of
every child subtree."

### `map`

```ocaml
let rec map (f : 'a -> 'b) (Node (x, children)) : 'b rose =
  Node (f x, List.map (map f) children)
```

`map f` applies `f` to the value at the current node and recurses on
every child using `List.map`, applying the *tree* `map` (not `f`
itself) to each child, since each child is itself an `'a rose`.

### `fold`

```ocaml
let rec fold (f : 'a -> 'b list -> 'b) (Node (x, children)) : 'b =
  f x (List.map (fold f) children)
```

This is the general catamorphism for the type. `f` receives the
value stored at a node together with the list of *already-folded*
results for each child, and decides how to combine them into a
single `'b`. `size` and `map` are both special cases of `fold`:

```ocaml
let size' t = fold (fun _ child_sizes -> 1 + List.fold_left ( + ) 0 child_sizes) t
let map' f t = fold (fun x child_trees -> Node (f x, child_trees)) t
```

Running the test driver in `rose.ml` on the tree

```
        1
      / | \
     2  3  4
    /|     |
   5 6     7
```

confirms `size t = 7`, `size' t = 7` (agreeing with `size`), and that
`map ((*)2) t` doubles every value while keeping the same shape.

## Question 2: A Little Practice with Regular Expressions

### 1. C++ identifiers

**Regex:**  `[a-zA-Z_][a-zA-Z0-9_]*`

A letter or underscore, followed by zero or more letters, digits, or
underscores. See `regex_examples/identifiers.mll`.

Sample results:

| input        | result  |
|--------------|---------|
| `foo`        | VALID   |
| `_bar123`    | VALID   |
| `My_Class2`  | VALID   |
| `3illegal`   | INVALID (starts with a digit) |
| `has space`  | INVALID |

### 2. U.S. phone numbers

**Regex (mathematical form):**

```
\(\d\d\d\) \d\d\d-\d\d\d\d  |  \d\d\d-\d\d\d-\d\d\d\d
```

`ocamllex` doesn't support the `{n}` counted-repetition operator, so
in `regex_examples/phone_numbers.mll` a run of exactly 3 or 4 digits
is spelled out digit-by-digit:

```ocaml
let digit = ['0'-'9']
let d3 = digit digit digit
let d4 = digit digit digit digit
let phone = ('(' d3 ')' ' ' d3 '-' d4) | (d3 '-' d3 '-' d4)
```

Sample results:

| input             | result  |
|-------------------|---------|
| `(256) 555-0134`  | VALID   |
| `256-555-0134`    | VALID   |
| `256.555.0134`    | INVALID (wrong separators) |
| `(256)555-0134`   | INVALID (missing space)    |

### 3. Signed floating point numbers

**Regex:**  `[+-]?[0-9]+(\.[0-9]+)?`

An optional leading sign, one or more digits, and an optional decimal
point that (if present) must be followed by at least one more digit.
See `regex_examples/floats.mll`.

Sample results:

| input     | result  |
|-----------|---------|
| `42`      | VALID   |
| `+42`     | VALID   |
| `-3.14`   | VALID   |
| `-.5`     | INVALID (no digit before the point) |
| `1.`      | INVALID (no digit after the point)  |

### 4. Binary palindromes of length 3 or 4

**Why this isn't "really" a regex problem:** the language of *all*
binary palindromes (any length) is not regular. Recognizing an
arbitrary-length palindrome requires remembering the entire first
half of the string so it can be compared against the reverse of the
second half, and a finite-state machine only has finitely many
states — it can't count/remember an unbounded amount of information.
It's naturally a context-free language, generated by a grammar like

```
S -> 0 S 0 | 1 S 1 | 0 | 1 | epsilon
```

which is exactly the "think recursively" structure the hint points
at: strip a matching bit off each end and recurse on what's left.

**The sneaky part:** we were only asked about length 3 *or* length
4, not arbitrary length. A language whose strings are all bounded to
a fixed set of lengths only ever contains finitely many strings, and
*every finite language is regular* — you can always write it down as
a plain enumeration (`OR`) of its members. So instead of trying to
force the recursive "match outside, recurse on inside" idea directly
into a regex (which is impossible for a general recursive/CFG
pattern), we run that recursion once ourselves, ahead of time, and
flatten the results into an alternation:

- length 3, shape `b0 b1 b0`: `000`, `010`, `101`, `111`
- length 4, shape `b0 b1 b1 b0`: `0000`, `0110`, `1001`, `1111`

**Regex:**

```
000 | 010 | 101 | 111 | 0000 | 0110 | 1001 | 1111
```

In `regex_examples/palindromes.mll` this is written directly as an
`ocamllex` alternation of string literals, and cross-checked against
an independent recursive `is_palindrome` function (the direct
transcription of the `S -> 0 S 0 | 1 S 1 | ...` idea) to confirm the
enumeration is complete and correct:

| input   | ocamllex regex | recursive check agrees? |
|---------|-----------------|--------------------------|
| `101`   | VALID           | yes |
| `0110`  | VALID           | yes |
| `100`   | INVALID (not a palindrome) | yes |
| `10101` | INVALID (wrong length, even though it *is* a palindrome) | yes |

## Question 2 (cont'd): Working with a Grammar

Grammar:

```
Expr   -> Expr + Term | Expr - Term | Term
Term   -> Term * Factor | Term / Factor | Factor
Factor -> ( Expr ) | number
```

Trees below are drawn top-down as nested outlines; each line's
indentation level is one more step down the tree than its parent.

### 1. `(3+(2*6)/2)`

```
Factor
├─ "("
├─ Expr
│  ├─ Expr
│  │  └─ Term
│  │     └─ Factor
│  │        └─ number(3)
│  ├─ "+"
│  └─ Term
│     ├─ Term
│     │  └─ Factor
│     │     ├─ "("
│     │     ├─ Expr
│     │     │  ├─ Expr
│     │     │  │  └─ Term
│     │     │  │     └─ Factor
│     │     │  │        └─ number(2)
│     │     │  ├─ "*"
│     │     │  └─ Term
│     │     │     └─ Factor
│     │     │        └─ number(6)
│     │     └─ ")"
│     ├─ "/"
│     └─ Factor
│        └─ number(2)
└─ ")"
```

The outermost parentheses force the whole thing through `Factor -> (
Expr )`. Inside, `2*6` is grouped by its own parentheses and divided
by 2 *before* being added to 3, because `Term -> Term / Factor`
binds `(2*6)/2` together as a single `Term`, and that whole term is
what gets added to `3` at the `Expr` level. Evaluates to `3 + 12/2 =
9` (confirmed by `parser/expr_parser.ml`).

### 2. `4*(3+2)*4`

```
Expr
└─ Term
   ├─ Term
   │  ├─ Term
   │  │  └─ Factor
   │  │     └─ number(4)
   │  ├─ "*"
   │  └─ Factor
   │     ├─ "("
   │     ├─ Expr
   │     │  ├─ Expr
   │     │  │  └─ Term
   │     │  │     └─ Factor
   │     │  │        └─ number(3)
   │     │  ├─ "+"
   │     │  └─ Term
   │     │     └─ Factor
   │     │        └─ number(2)
   │     └─ ")"
   ├─ "*"
   └─ Factor
      └─ number(4)
```

There is no top-level `+`/`-`, so `Expr -> Term` fires once at the
root. Left-associative `*` groups as `(4 * (3+2)) * 4`, i.e. the left
`Term * Factor` production is applied twice, each time attaching the
new factor on the right — exactly the left-associativity guaranteed
by left recursion. Evaluates to `4*5*4 = 80`.

### 3. `42*1+3*(80+90)`

```
Expr
├─ Expr
│  └─ Term
│     ├─ Term
│     │  └─ Factor
│     │     └─ number(42)
│     ├─ "*"
│     └─ Factor
│        └─ number(1)
├─ "+"
└─ Term
   ├─ Term
   │  └─ Factor
   │     └─ number(3)
   ├─ "*"
   └─ Factor
      ├─ "("
      ├─ Expr
      │  ├─ Expr
      │  │  └─ Term
      │  │     └─ Factor
      │  │        └─ number(80)
      │  ├─ "+"
      │  └─ Term
      │     └─ Factor
      │        └─ number(90)
      └─ ")"
```

The top-level `+` splits the expression into `42*1` on the left and
`3*(80+90)` on the right, each of which reduces through `Term ->
Term * Factor` before the addition ever happens — `*` binds tighter
than `+` because `Term`s (built from `*`/`/`) are what `Expr`'s `+`/
`-` production combines, never raw numbers directly. Evaluates to
`42 + 3*170 = 552`.

## Question 3: Extending the Expression Grammar (unary +/-)

Unary `+` and `-` need to bind *tighter* than `*`, `/`, and grouping
— `-3*4` should mean `(-3)*4`, and `-(3+4)` should apply the minus to
the whole parenthesized value. So a new `Unary` nonterminal is
inserted between `Term` and `Factor`: `Term` now multiplies/divides
`Unary`s instead of `Factor`s directly, and `Unary` either peels off
a sign (recursively, so `--3` and `-+3` both parse) or falls through
to a `Factor`.

```
Expr   -> Expr + Term
        | Expr - Term
        | Term

Term   -> Term * Unary
        | Term / Unary
        | Unary

Unary  -> + Unary
        | - Unary
        | Factor

Factor -> ( Expr )
        | number
```

The unary productions are listed before `Factor` because `Unary` is
tried *before* falling back to a bare `Factor` — a sign must be
stripped off (if present) prior to parsing the underlying factor,
which is also why the sample parser in `expr_parser.ml` tries `+`/`-`
first in `parse_unary` and only calls `parse_factor` once no more
signs are found.

### Parse tree for `(3 + -3) * 4`

```
Term
├─ Term
│  └─ Unary
│     └─ Factor
│        ├─ "("
│        ├─ Expr
│        │  ├─ Expr
│        │  │  └─ Term
│        │  │     └─ Unary
│        │  │        └─ Factor
│        │  │           └─ number(3)
│        │  ├─ "+"
│        │  └─ Term
│        │     └─ Unary
│        │        ├─ "-"
│        │        └─ Unary
│        │           └─ Factor
│        │              └─ number(3)
│        └─ ")"
├─ "*"
└─ Unary
   └─ Factor
      └─ number(4)
```

`-3` is produced entirely within `Unary -> - Unary -> Factor ->
number(3)`, *inside* the parenthesized `Expr`, before that whole
parenthesized group is multiplied by `4` at the top. Evaluates to
`(3 + (-3)) * 4 = 0` (confirmed by `parser/expr_parser.ml`).

## Question 4: Extending the Expression Evaluator

`parser/expr_parser.ml` is a self-contained lexer + recursive-descent
parser + evaluator implementing the full grammar from Question 3
(`Expr`, `Term`, `Unary`, `Factor`, covering `+ - * /`, unary `+ -`,
parentheses, and integer literals). It follows the same technique as
the lecture starter for the single addition rule, extended to every
new production:

- Each grammar nonterminal (`Expr`, `Term`, `Unary`, `Factor`) is one
  parsing function.
- Left-recursive rules (`Expr -> Expr + Term | ...`, `Term -> Term *
  Unary | ...`) are each implemented as "parse one of the next level
  down, then loop consuming more operators and right-hand sides,"
  which produces left-associative trees without actual left
  recursion in the OCaml code (a hand-written recursive-descent
  parser cannot recurse on the same nonterminal without consuming a
  token first, or it would loop forever).
- `Unary -> + Unary | - Unary | Factor` *is* written as ordinary
  right recursion, since it's a right-recursive rule.

Build and run:

```
$ ocamlc expr_parser.ml -o expr_parser
$ ./expr_parser
(3+(2*6)/2)          parses as (3 + ((2 * 6) / 2))                = 9
4*(3+2)*4            parses as ((4 * (3 + 2)) * 4)                = 80
42*1+3*(80+90)       parses as ((42 * 1) + (3 * (80 + 90)))       = 552
(3+-3)*4             parses as ((3 + (-3)) * 4)                   = 0
-2*-3                parses as ((-2) * (-3))                      = 6
-(2+3)               parses as (-(2 + 3))                         = -5
+5 - -5              parses as ((+5) - (-5))                      = 10
```

Every result matches the value implied by the hand-drawn parse trees
above (9, 80, 552, and 0, respectively), which cross-checks both the
grammar work in Questions 2–3 and the parser implementation against
each other.
